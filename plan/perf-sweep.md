## §3 The editor path — one keystroke, traced

**Phone/iPad (`NoteBodyView.swift`, shared code, `UITextView`-backed):**
1. Keystroke lands in `UITextView`; UIKit updates its own `NSTextStorage` natively — no Skrift code runs yet.
2. `textViewDidChange` (`:1043`) fires: `markDraftDirty()` (:215, sets two bools — no disk, no store).
3. `refreshAccessory()` (:670) — reads `undoManager` state + `caretInTaskLine()`, which scans only the caret's current line (:677-685), not the document.
4. `detectLinkTrigger(tv)` (:1149) — reads 2 characters before the caret, O(1).
5. `commitTask` is cancelled and rescheduled 1 second out (:1048-1053) — **touches disk/store** only after 1s of no further typing.
6. On commit (`:1163`), `commitDraft()` reconstructs the marker string from the attributed text (O(note length), not O(corpus)) and writes to `memo.transcript`/the polish binding — **touches the store**, once per pause, not per keystroke.

**Mac (`BodyTextView.swift` via `NoteBody.swift`, `NSTextView`-backed):**
1. Keystroke lands in `NSTextView`; `textDidChange` (`:232`) fires **synchronously, every character, no debounce**.
2. `parent.text = modelString(tv)` (:234, function :1019) — walks the ENTIRE `NSTextStorage`, enumerating every attachment across the full range to rebuild the marker string — **touches the store immediately**: `bodyBinding`'s setter (`NoteBody.swift:209-212`) writes straight into `file.transcript`/`.sanitised`/`.enhancedCopyedit` on the SwiftData model, then calls `MacCloudEditSync.shared.note(file)` (itself debounced 1.5s — the sync push is fine, the model write and the restyle are not).
3. `restyle(tv)` (:235, function :651) — clears and reapplies `.foregroundColor`/`.font`/etc over the full text range, enumerates every attachment again, runs `linkRegex` and `turnHeaderRegex` over the whole string, walks `BodyMarkdown.headings`/`inlineTags`, walks `suggestedRanges` — **all over the full document, every keystroke**.
4. `tv.invalidateIntrinsicContentSize()` (:236) — triggers a relayout pass.
5. `maybeShowLinkPicker(tv)` (:237), `updateTagSuggest(tv)` (:238) — bounded to the caret's `#word`/`[[` run, cheap (comment at :248 already fixed a prior full-library-fetch-per-keystroke bug here).

Steps 2-4 on the Mac run unconditionally on every character with no debounce, over the full document, and step 2 writes the model directly. This is the concrete mechanism behind "note writing is quite slow and clunky" — and it scales with note length, so it will read worst on the longest/most-edited notes, which are also the ones Tuur is most likely to be hand-polishing.

## §5 For Tuur

It feels slow because almost every screen re-scans the whole note corpus or the whole current note on actions that should be O(1) — list rows, note-open, and (new this pass) every single keystroke in the Mac editor, which rebuilds and restyles the entire document and writes the model directly with no debounce. The single worst thing is the Mac editor path (`BodyTextView.swift` restyle + `modelString`, §2 #1) — it is the most direct match to "note writing is slow and clunky" and it gets worse the longer the note. Nothing here is measured, so before fixing: run ⌘I Time Profiler on the prod iPhone 13 build per AUDIT_PLAN §0, and separately time a long-note typing session on the Mac, to confirm these are the frames actually being spent before you spend a day on any of them.
