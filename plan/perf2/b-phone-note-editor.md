# Phone note screen and typing: speed sweep (read-only, 2026-10-05)

1. HIGH: Opening a note runs corpus-wide work on the main thread in `MemoPageView.task(id: memo.id)` (:130-140), once per realized pager page. It scans every transcript and copy-edit for backlinks, and builds a title for every note via `ladderTitle()`, which runs 5 regexes over the whole body (N1, N2).
2. HIGH: Playing a 6,000-word conversation note turns the whole transcript into one SwiftUI `Text` per word inside a non-lazy `FlowLayout`, and the body is re-evaluated at the 20 Hz clock tick (N3).
3. HIGH: Every typing pause (the 1 s commit) triggers a corpus cascade: Memo save, a second save plus a full body copy into `MemoEditHead`, the list's `editHeads` @Query refetch, and `EditConflictWatch.refresh`, which fetches all live Memos and all heads (N4, N5). The hitch lands as the user resumes typing.

Everything below is from reading the call chain. Nothing was built, run or measured. Millisecond figures are order-of-magnitude guesses, marked "suspect" where I did not follow the whole chain. "Neighbour pages realized" rests on the code comment at `MemoDetailView.swift:576` ("The LazyHStack realises adjacent pages"), which I did not confirm on a device.

## Notes on what looks fine (checked, no finding)

- Per-keystroke path in the phone editor is otherwise light: `textViewDidChange` marks dirty, refreshes the accessory (about 4 `UIColor(Color)` conversions), and detects "[[" in O(1). It cancels and reschedules a 1 s commit Task. No SwiftData work per keystroke. (The N10 re-measure is the exception.)
- Karaoke for monologue notes repaints only the changed words per tick (`NoteBodyView.swift:452-463`), and the 20 Hz clock never goes through the SwiftUI tree (`PlayerClock`, `AudioPlayerModel.swift:11-13`).
- Phone has no markdown styling or tag typeahead in the note body (those are Mac-only); `TagEditorRow` completes from the small `allTags()` list.
- `MemoImageLoader` downsamples via ImageIO and caches in NSCache, keyed by path + mtime + size.
- `CommitDebouncer`/`CommitOnceCache` are used correctly. The only issue is the single slot on `SpeakerTranscript.parseCache` (N8).
- `DevLog.log` is an `@autoclosure` and DEBUG-only, so the `display.count` interpolation at `NoteBodyView.swift:344` costs nothing in Release.
