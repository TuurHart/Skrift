# Sweep A — phone/iPad note screen + editor (read-only, 2026-09-25)

Scope: `SkriftMobile/Features/MemoDetail/`, `Features/QuickNote/`, the Shared code they
call per keystroke/commit. Read `plan/perf-sweep.md` and `plan/perf-measured.md` first —
items already filed there (P1-P7, R90-R94, known-still-open) are cited, not repeated in
full. All findings below verified by reading the current code in this worktree.

## Ranked findings

1. `Skrift_Native/SkriftMobile/Services/QuickNote/QuickNoteDraft.swift:20-31` + `Features/QuickNote/QuickNoteView.swift:104,115` — **SLOW.** `onChange(of: title)`/`onChange(of: bodyText)` fire `draft.edited(...)` on EVERY character typed in Quick Note (the widget/Siri/Lock-Screen fast-capture screen); `edited()` calls `memo.markEdited()` (schedules a SHA256 hash of the whole note, see #4) and `try? context.save()` synchronously, no debounce. `NoteBodyView`'s own doc comment says "Saves are DEBOUNCED (the old per-keystroke `context.save()` is gone)" — that fix never reached Quick Note. Cost: O(1) SwiftData save + O(document) hash per keystroke, unthrottled. Fix: debounce `edited()` the same 1s way `NoteBodyView.Coordinator.textViewDidChange` does. Confidence: high.

2. `Features/MemoDetail/MemoDetailView.swift:914,1564,1612,1633,1749(via macPolish)` — **SLOW + INELEGANT.** `SpeakerTranscript.parse(memo.transcript)` is called at 5+ separate sites in this one file (the page-kind switch, `conversationContent`, `recomputeSpans`, `startAssigning`, `macPolish`) — every call compiles a fresh `NSRegularExpression` (already P6 in perf-sweep, uncached) and rescans the full transcript. A single body re-eval or debounced commit can run this 3-4x on the same text. Fix: parse once into a cached `@State`/computed value keyed on `memo.transcript`, have every site read that. Confidence: high.

3. `Features/MemoDetail/MemoDetailView.swift:932,935,1171-1177,1610-1625` — **INELEGANT (duplicate work).** `onCommit` (the debounced editor commit) calls `recomputeSpans()` directly at line 1176; `memo.transcript` changing under a `.raw` commit ALSO fires `.onChange(of: memo.transcript)` at line 935, which calls `recomputeSpans()` again (a `.polished` commit double-fires via `.onChange(of: macPolish?.copyedit)` at 932 instead). Every commit therefore runs `recomputeSpans()` — a `SpeakerTranscript.parse` + a `Task.detached` `Sanitiser.nameSpans` scan — twice. Fix: pick one trigger (the `onChange` alone would cover both raw and polished cases) and drop the direct call from `onCommit`. Confidence: high.

4. `Shared/Model/EditConflict.swift:109-113,282-288` — **SLOW.** `EditConflicts.hash(memo)` (called from every `markEdited` via `scheduleEditStamp`) does `SHA256.hash` over the FULL title+body+tags string. Fired once per debounced commit in the real editor (cheap there) but once per KEYSTROKE in Quick Note (#1) with no coalescing — `DispatchQueue.main.async` schedules one closure per keystroke, each re-hashing the whole growing note. Fix: coalesce with the same debounce as #1, or hash incrementally. Confidence: high.

5. `Features/MemoDetail/MemoDetailView.swift:1541,1550-1557` — **SLOW.** `liveLinkTitle(_:)` and `memoLinkCandidates()` both call `repository.allMemos()` — a full sorted `FetchDescriptor<Memo>` over the whole corpus — to find ONE memo by id (`liveLinkTitle`, via `.first(where:)`) or to list link candidates. `liveLinkTitle` is the `linkTitle` closure handed to `NoteBodyView`, invoked once per memo-link chip inside `NoteBodyView.Coordinator.attributed(from:)` on every `load(force:)` rebuild — so a note with N link chips does N full-corpus fetches per rebuild. Fix: a `NotesRepository.memo(id:)` single-predicate fetch. Confidence: high.

6. `Features/MemoDetail/MemoDetailView.swift:1478` — **SLOW.** `loadRelated()` calls `repository.allMemos()` (full corpus, sorted) just to build an `id → Memo` dictionary for looking up a handful of already-scored related IDs from `JournalIndexService`. Fix: fetch only the scored ids (`FetchDescriptor` with an `id` predicate, or a repository helper that takes `Set<UUID>`). Confidence: high.

7. `Features/MemoDetail/MemoDetailView.swift:1486-1508` (`recomputeBacklinks`) — **SLOW.** `repository.allEnhancements()` and `repository.allMemos()` both fetch the FULL unfiltered corpus; the dictionary build + per-memo body concatenation (lines 1491-1500) happens synchronously on the main actor BEFORE the `Task.detached` scan starts — the corpus fetch/map itself isn't offloaded, only the substring search is. Same shape as the known "note opening scans the corpus twice" item in perf-sweep §2 #5. Fix: move the fetch+map into the detached task too. Confidence: high.

8. `.task(id: memo.id)` block, `MemoDetailView.swift:920-928` — **SLOW**, confirms perf-sweep's still-open "note opening scans the corpus twice per pager page" (§1). Every note open/pager-page re-run does `NamesStore.shared.livePeople()` (fresh `names.json` decode, P7), `recomputeBacklinks()` (#7 above), and `MemoLifecycle.backlinkedIDs(in: repository.allMemos())` — a third full-corpus fetch. Fix per perf-sweep's R-row direction: cache/memoize `NamesStore`, single-source the corpus fetch across these three calls. Confidence: high (re-confirmed, not new).

9. `Features/MemoDetail/SpeakerTurnsView.swift:148` inside `segmentItems`, called from the `ForEach` at line 113 — **SLOW**, confirms perf-sweep §2 #9 (still present): a fresh `NSRegularExpression` is compiled on every call, i.e. once per turn per render of a conversation note. Fix: hoist to a `static let`. Confidence: high (re-confirmed).

10. `Features/QuickNote/QuickNoteBodyTextView.swift:63-67` vs. `Features/MemoDetail/NoteBodyView.swift` — **INELEGANT.** Quick Note runs a second, much simpler `UITextView` + `UITextViewDelegate` implementation with no debounce, no attributed-text pipeline, and no shared commit path with the real editor's `Coordinator`. The two editors don't share the throttling logic that #1 shows Quick Note is missing — a single shared "debounced text commit" helper (in `Shared/`) would fix #1 once instead of twice. Confidence: high.

11. `Features/MemoDetail/MemoDetailView.swift:15-2578` — **INELEGANT.** One `struct MemoDetailView` is 2,563 lines with 138 `private func`/`private var`/`@ViewBuilder` members: pager/player wiring, name-resolution UI + sheets, capture-content layout, conversation routing, backlinks, related-memos retrieval, photo insertion, speaker-assign, reminder sheet, and Mac-polish binding all live in one type. Companion views already split out (`ConnectionsPanel.swift`, `SpeakerTurnsView.swift`, `CaptureVoiceAnnotate.swift`) show the seam exists; the glue/state (name resolution, backlinks, related, photo insert) never followed. Fix: extract name-resolution and backlinks/related into their own `@Observable` view-models, matching the pattern already used for the split-out views. Confidence: med (structural judgment call, not a bug).

12. `Features/MemoDetail/NoteBodyView.swift:1220-1224` (`committedBody`) — **INELEGANT**, minor: recomputes `BodyV2Marker.runs(in:manifestCount:)` on every commit even for notes with zero images (guard falls through to `return text` only after the scan runs). Cheap per-commit (1s debounce), listed for completeness only — not worth a fix on its own. Confidence: med.

13. `Shared/Naming/Sanitiser.swift:221+` (`nameSpans`) — **SLOW**, context for #3: each `recomputeSpans()` call dispatches a fresh `Task.detached` running this full-document name scan (builds `Overrides`, `nonProseRanges`, iterates all people × aliases). Off-main so it doesn't block typing, but #3's double-fire means it runs twice per commit for no reason — fixing #3 halves this cost for free. Confidence: high.
